# Goggles Bridge 0.3.1 改动明细与提交准备

0.3.1 打磨 0.3.0 的上游桌面端集成：恢复普通桌面的高级设置，让每个可见选项真实生效；把虚拟屏所需配置限制在虚拟屏会话中；保留作者的界面结构、Windows NVENC 后端和已验证的虚拟屏生命周期。

本版本是配置兼容性和交互修复，按本 fork 的版本规则使用补丁版本 `0.3.1`。工作分支为 `codex/polish-upstream-options-v0.3.1`，基于 `codex/upstream-app-performance-v0.3.0`。作者仓库基线为 `Ammaar-Alam/goggles-bridge` 的 `e88bb484f6643e98ed2785698b272a3f8399f0db`。

## 1. 本次修复了什么

| 项目 | 0.3.0 的行为 | 0.3.1 的处理 | 用户可以观察到的变化 |
| --- | --- | --- | --- |
| 原作者高级选项 | Windows 只显示编码 preset；其他控件被能力标记隐藏 | 普通桌面恢复原作者选项，后端和编码命令同时传递设置 | 选项不再只存在于 SDK/命令行中 |
| 捕获方式 | 强制 DDA；打包的定制 FFmpeg 没有 WGC | 普通桌面支持 DDA 和 WGC；为 WGC 使用上游固定版本的 FFmpeg | 原捕获方式可选，不会静默改成另一种 |
| H.264 Profile / AQ / 低延迟 | 部分字段在保存或运行时被全局强制覆盖 | 普通桌面采用用户设置；虚拟屏仅为本次会话应用固定配置 | 从虚拟屏切回普通桌面后，原偏好仍保留 |
| 关键帧间隔 | 实际使用启动阶段关键帧，界面却不再提供原选项 | 保留应用层 Startup only，恢复 1 秒和 3 秒周期选项 | 能明确选择当前优化行为或周期恢复行为 |
| USB 写入块大小 | 控件被一并隐藏，虽然并非虚拟屏不适用 | 两种来源均保留 2 KB / 16 KB 选择 | 不再因选择虚拟屏而失去有效高级选项 |
| 来源名称 | `Separate display` | 来源选项显示为“虚拟屏” | 按本 fork 用户要求简化名称 |
| 停止时异常 | 停止标志可能把真实清理失败当作正常取消 | 保留有意义的错误与退出状态，验证清理失败路径 | 清理失败不会被误报为成功结束 |
| 诊断使用的编码器版本 | 双构建接入过程中，诊断可能仍显示 native 版本 | 报告当前来源实际选择的 FFmpeg 路径与版本 | WGC 问题不会被误归到 DDA 构建 |
| 未使用的遥测代码 | 仍保留未接入当前 worker 的采样包装 | 删除未使用的采样模块、对应专属测试及闲置代码 | 减少后续上游审查范围；不改变已停用的热路径统计 |

高级选项原本就存在于上游。这里修复的是 **0.3.0 集成时隐藏和强制覆盖了它们的回归**，不是声称作者的 app 缺少这些功能。

## 2. 哪些选项在虚拟屏下显示

| 选项 | 普通桌面 | 虚拟屏 | 设计原因 |
| --- | --- | --- | --- |
| Capture method | DDA / Windows Graphics Capture | 隐藏，使用 DDA | 虚拟屏使用已验证的原生捕获路径 |
| Keyframe interval | Startup only / 1 second / 3 seconds | 隐藏，使用 Startup only | 保留此前消除周期性闪烁的会话策略 |
| H.264 profile | High / Baseline | 隐藏，使用 High | 继续使用已验证的虚拟屏编码策略 |
| Encoder preset | p1 / p4 | p1 / p4 | 两种来源均适用 |
| Adaptive quantization | 开 / 关 | 隐藏，关闭 | 虚拟屏保持当前稳定配置 |
| Low-latency delivery | 开 / 关 | 隐藏，开启 | 虚拟屏保持当前低延迟交付路径 |
| USB write size | 16 KB / 2 KB | 16 KB / 2 KB | 是传输选项，与显示来源独立 |

虚拟屏的限制只作用于“有效运行配置”，不覆盖普通桌面的已保存偏好。界面隐藏不是删除配置：切换来源会恢复普通桌面的选择。

周期关键帧和关闭低延迟交付属于可选行为。周期完整帧可能增大瞬时帧尺寸，关闭低延迟交付可能增加等待；恢复这些选择不代表所有组合都比默认更快。Startup only 保留为已有优化用户的默认，不把已报告的固件现象隐瞒在参数后面。

## 3. 怎么改动

### 配置与迁移

`goggles_bridge/app/backend.py` 将普通桌面偏好、虚拟屏有效配置和 SDK 参数区分开来。普通桌面设置不再被全局强制为 DDA/High/AQ off/低延迟 on；切换到虚拟屏时使用临时副本。

关键帧的 `0 = Startup only` 是桌面 app 的扩展值。进入 SDK 前会生成合法的 `BridgeSettings`，随后在编码器适配层应用启动关键帧策略；没有将 `0` 加入共享 SDK 的 `CHOICES`，也没有改变原命令行的 1/3 秒参数约定。

迁移区分来源：0.3.0 里已经采用启动关键帧的集成配置继续保留该行为；来自上游、没有本 fork 来源字段的设置继续保留作者原来的 1/3 秒选择。这样修复高级选项时不会顺带改变已有用户的实际编码策略。

### 捕获与编码

`goggles_bridge/app/windows/video.py` 和 `worker.py` 负责把来源与选项转为实际命令。DDA 继续使用已验证的定制 FFmpeg、GPU 色彩转换和有界帧调度。WGC 使用上游固定版本的 FFmpeg，而不是让一个没有 `gfxcapture` 的二进制接收无效命令。

来源通过稳定的 Windows 显示器标识解析；DDA 绑定实际 DXGI adapter/output，WGC 绑定选中显示器的 HMONITOR。编码预检和实际串流经过同一适配策略，避免“预检用一套参数、启动时用另一套”的差异。两条 Windows 路径均仍使用 NVIDIA NVENC，不回退到软件编码。

`packaging/build_windows.py` 与路径解析配合提供两个有明确用途的 FFmpeg，并保留各自版本、校验和许可证说明。增加此依赖是恢复原 WGC 选项所需；它不意味着替换掉已经验证过的 DDA native build。

### 交互与审查范围

`goggles_bridge/app/ui/app.js` 沿用作者已有的高级控件，按当前来源决定显示条件；`demo.js` 与界面回归相应覆盖物理/虚拟来源切换。没有更换原页面布局、图标、配色或制作另一套桌面 UI。

停止、异常和清理路径继续由独立 worker 管理。去掉未使用的 `device.py` / `telemetry.py` 及相关闲置代码和专属测试，共移除 163 行，减少“看似有实时功能、实际未接入”的维护负担。原生视频字节仍不经过 WebView 进程。

## 4. 对上游改动是否足够小

这里的“最小”指尽量保持作者原有默认行为和模块边界，而不是宣称整个发行分支只有几行差异。

| 范围 | 当前处理 |
| --- | --- |
| USB 包格式、控制协议、会话状态机 | 继续使用上游实现，不为 UI 选项重新实现协议 |
| 共享 SDK 选项集合 | 不因 app 的 Startup only 扩展而扩大 |
| macOS 捕获与打包 | 保留原路径；本轮没有 macOS 新功能 |
| 原作者 UI | 复用既有结构和控件，只增加来源/模式/生命周期所需内容 |
| Windows 增量 | 留在 `app/windows/` 及明确的 app 适配点 |
| 定制 FFmpeg | 保留单独原生补丁和构建输入；它仍是相对较大的贡献，必须单独审查 |
| fork 发行安排 | 版本、更新源、安装器、本地教程不应自动进入第一条上游性能 PR |

0.3.0 已加入的完整虚拟屏驱动管理、定制 native FFmpeg 和发行流程，仍使整个 fork 比上游大得多。本轮减少不必要的覆盖与闲置代码，不把“大而完整的发行分支”说成“最小 PR”。真正向上游贡献时应按[首次 PR 演练](contributing/FIRST-PR.zh-CN.md)整理专题分支。

## 5. 优化前后效果：哪些是事实，哪些尚未测量

| 比较项 | 可以确认的改善 | 不能据此推出的结论 |
| --- | --- | --- |
| 高级设置 | 从隐藏/被覆盖改为可选择且命令真实生效 | 所有高级参数组合都提高性能 |
| 来源切换 | 普通桌面偏好不被虚拟屏固定策略覆盖 | 切换来源不会改变任何操作系统调度 |
| WGC 兼容 | 有实际支持该滤镜的固定构建 | 与 DDA 在所有显卡、场景、固件上效果一致 |
| 清理错误 | 不再因停止标志吞掉失败 | 断电、强杀进程也能执行 Python 清理 |
| 减少遥测代码 | 去掉未使用的实现与依赖 | 新测得降低了多少毫秒延迟 |

本轮重点是配置、交互和兼容性打磨，**没有将它宣称为一次新测得的延迟或画质提升**。用户反馈 0.3.0 已明显改善体验，可以作为使用反馈；它不等同于受控硬件 A/B 结果。

此前 0.3.0 的记录可作为已有链路背景：[验证说明](WINDOWS-0.3.0-VALIDATION.md)。其中 1080p100 / 40 Mbps / P4 的短时 USB 串流，在启动之后两个完整 5 秒区间记录到 100.05 和 100.00 fps、USB send p95 1.04/0.99 ms，且无超大帧。首个区间含启动过程，为 82.38 fps。场景是桌面，并非 FPV 游戏；这些值不是新版本光学延迟，也不能证明每帧间隔在 ±1% 内。

作者的约 12 ms 结果有自己的 GPU、固件、显示器、测量方法和场景；不能与这里的 USB send p95 直接相减或计算“提升百分比”。光学测量方法仍以 [LATENCY.md](LATENCY.md) 为准。
