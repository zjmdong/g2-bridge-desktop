# DJI Goggles Streamer 0.2.5

## 安装与使用

1. 运行 `DJI-Goggles-Streamer-0.2.5-Setup.exe`，为当前用户安装或升级，保留设置。
2. 在「设备与驱动」确认 H.264 编码测试通过，连接已开机的眼镜。
3. 缺少 USB 驱动时点击「下载并安装驱动」，或导入 DJI Assistant 2 消费机系列
   2.1.42 离线安装包。首次官网下载约 354 MiB；客户端校验后提取驱动，管理员
   授权由用户在 Windows 中完成。不捆绑 DJI 固件或未经许可的 DJI 安装程序。
4. 在眼镜中进入「更多 → DJI Virtual Flight」。默认开启 USB 插入自动串流，
   也可关闭该选项后手动开始。手动停止后，下次重新插线才再次自动开始。
5. 停止、拔线或退出客户端时释放编码、USB 和串流扩展屏。

需要 Windows 10 2004 / Windows 11 x64、支持 Desktop Duplication 的显示驱动
和数据线，以及支持 H.264 NVENC 的 NVIDIA 显卡和驱动。0.2.5 仅使用 NVIDIA
硬件编码，不提供软件编码或软件回退。NVENC 初始化失败时会提示修复驱动，
不会通过 CPU 编码继续串流。P1 为速度优先，P4 为画质优先；实际游戏负载和
显示刷新节奏仍会影响流畅度。NVIDIA 显示输出的缩放和色彩转换在 GPU 完成；
混合显卡电脑若画面来源属于另一厂商的显卡，需要经过 CPU 中转，仍使用 NVIDIA 编码。

SDK 已测试固件：Goggles 2 01.11.00.00 / 01.14.00.00、Integra 01.09.00.00。
本客户端此前的人工验收使用 Goggles 2 01.14.0000；不代表本版已完成新的光学测量。
01.12 有上游黑屏报告，未知
版本会阻止串流。客户端提供官方更新/恢复教程，不自动刷机；可升级或降级的
版本以 DJI 官方工具实际列表为准。

## 画面参数

可选择电脑主屏或独立扩展屏；特定窗口选择和 macOS GUI 尚未实现。
两档分辨率：1280×720 / 1920×1080。扩展屏刷新率跟随目标帧率，眼镜面板
实际刷新率仍由设备决定。主屏等比缩放并补黑边，保留带鱼屏原有分辨率、
刷新率与主屏状态。Desktop Duplication 不显示 WGC 的黄色采集边框。
FPV 的默认目标为 1080p / 100 fps / 20 Mbps / NVIDIA P4。电脑主屏与独立扩展屏
共用同一采集和发送策略。60 Hz 主屏每秒最多产生 60 个不同画面，目标 100 fps
不会将其变成 100 Hz；扩展屏可按 100 Hz 创建。游戏自身的帧率和呈现队列仍需
跟上目标刷新率，客户端不会修改主屏或模拟器的设置。

| 帧率 / 扩展屏刷新率 | 最高码率 |
| --- | --- |
| 60 fps / Hz | 24 Mbps |
| 75 fps / Hz | 30 Mbps |
| 90 fps / Hz | 32 Mbps |
| 100 fps / Hz | 40 Mbps |

全部码率在界面中可见，超出当前 SDK 预算的选项标明最低帧率并禁用。
SDK 的 50,000 字节平均帧预算和 56,000 字节单帧保护保留。
设定码率是编码目标，静止画面的实际传输量通常较低。

## 独立扩展屏

首次选择此来源并安装内置签名 VDD 25.7.23 驱动。从旧版升级时点击「更新
扩展屏配置」，完成管理员授权，启用两种分辨率与四档刷新率。
开始串流时自动创建主屏右侧的 Windows 桌面，用 Win + Shift + → 移动模拟器，
或在模拟器内部选择该显示器。停止或拔线自动收回桌面，Windows 重新安排窗口；
驱动保留以供下次使用，无需反复安装或手动启用、断开。

此功能由虚拟显示驱动提供独立桌面，再由 SDK 经 USB 发送给眼镜，不是把眼镜
USB 改造成物理 DisplayPort。客户端只管理自身安装的唯一 VDD，不覆盖其他
软件配置；多个同类虚拟显示器会拒绝自动选择。驱动保留原签名，不导入证书
或关闭签名验证。「移除扩展屏驱动」需要管理员授权，卸载应用不自动删除系统
驱动。参考：[VDD 官方说明](https://github.com/VirtualDrivers/Virtual-Display-Driver/tree/25.7.23)。

## 图像和流畅度

当前版本在 GPU 上将 SDR 桌面转换为 BT.709 限幅 NV12，等比缩放并使用正确的
黑边电平 Y=16、U/V=128。仅在放大较小来源时，先放大 RGB，再等尺寸转换为
NV12，避免本机驱动同时放大和色度采样时出现的边缘偏色；等尺寸和缩小只需一次转换。
生成图回归检查覆盖 16∶9、带鱼屏和竖屏比例，以及两档输出分辨率。
这些有限内容的电脑端检查不代表所有眼镜显示或驱动组合均已验证；
具体结果见本版验证记录。

0.2.5 改用 H.264 High / CABAC，提高固定码率目标下的运动压缩效率，减少
快速运动与细纹理的量化失真，并调整色度量化以改善颜色边缘；RGB 转换和缩放不变。
仍为 NVENC 超低延迟模式，无 B 帧、单参考帧，
关闭前瞻和周期性帧内刷新，没有增加输出缓冲或改变所设码率。
保留 SDK 的四分之一分辨率双遍码率控制（qres）、约两帧目标量的 VBV 预算及
单帧保护限制。20 Mbps / 100 fps 时 VBV 为 400,000 bits；它是码率控制预算，
不是每帧强制等待 20 ms，也不保证每帧大小或每个时间窗口的码率完全相同。
0、1、2 秒提供关键帧建立解码画面，随后取消会引起周期闪烁的强制 IDR。
仅发送第一个关键帧在验收设备上会黑屏，因此保留启动阶段的重复关键帧。
传输失败或超大帧后，SDK 重启编码并重新执行启动阶段。

采集直接按所选帧率使用 QPC 高精度时钟调度，不再从 240 Hz 轮询结果筛选
100 fps。采集源直接进入处理滤镜图，避免额外的输入和解码队列。
编码前最多保留一张等待画面；负载过高时，新画面替换尚未编码的旧画面，
防止积压持续增加画面年龄。因此本版不承诺过载时零丢帧；已经编码的 H.264
参考帧仍按顺序发送，不通过任意丢弃 P 帧追赶。编码后没有额外节拍等待。

继续沿用 0.2.4 的桌面更新相位对齐：确认来源稳定更新后，将采集安排在估计更新时刻
之后约 3 ms，每次仅将后续采集时机微调最多 ±100 微秒。重复画面、仅鼠标更新
及不可靠的时间样本不参与估计。该设置用于减少刚好错过桌面更新的情况，不是
新增 3 ms 编码缓冲，也不会为了保持节奏自动降低码率。它无法同步未公开的
眼镜显示时钟，也不能使不足 100 fps 的来源产生 100 张新画面。

继续沿用 0.2.4 的 High（4）GPU 调度请求，
仅在编码开始时设置一次，并在日志中记录 Windows 是否接受。该策略不修改
模拟器或其他进程，不保证所有驱动和负载下的等待时间恒定。

NVENC 使用异步完成事件，图像就绪后才读取码流。FFmpeg 子进程使用高于普通
的 CPU 优先级，并尽可能关闭该进程的节能降速及计时器忽略策略；不修改系统
全局电源计划或使用 CPU 实时优先级。这些措施减少可避免的等待，不能让 Windows
成为硬实时系统。会话日志仍异步写入，FFmpeg 周期进度输出保持关闭。
两种来源不再有不同的应用等待策略，但物理屏、虚拟屏和游戏呈现时序仍不同，
无法仅凭源码保证输入到眼镜的物理延迟完全相等。
受保护内容不能采集，部分独占全屏或远程桌面需要改用窗口或无边框全屏。

## 实时统计和 USB

每次成功发送时记录计数与 USB 写入耗时，独立线程约每 100 ms 更新界面。
带宽、帧率使用最近一秒窗口。统计不在视频线程排序、绘图或写 IPC；界面卡住
时只保留最新统计，不能反向阻塞视频发送。
当前版本保留这些低开销计数，串流进程内不再重复执行每 250 ms 全量 PnP 检查。
独立 USB 插拔监听继续工作；SDK 会话异常后会再确认设备是否拔出。

USB 发送耗时不包含采集、编码、调度等待或眼镜显示。SDK 不返回眼镜显示
时间戳，无法由这些计数得到实时端到端延迟。带宽包含成功写入的协议和视频
字节，不包含 USB 总线开销。

原作者约 12.1 ms 为特定硬件、固件、240 Hz 参考显示器及原生 D3D11 路径的
显示器到镜片附加延迟，不是模拟器输入到眼镜的总延迟。本版未重新进行光学
延迟测量，不能将界面中的 USB 耗时或稳定发送帧率当作已经达到 12 ms 的证明。
也没有证明全程延迟或码率波动不超过 1%，或实现与直连显示器相同的无压缩传输。

SDK 的 MI04 通道为 512 字节 Bulk 端点，对应 USB 2.0 High Speed，理论总线
速率 480 Mbps。更快的电脑接口不会将此通道升级为 USB 3.x；视频速率还受
固件单帧预算与解码能力限制。客户端拒绝速度不足的 Full Speed 连接。
USB Bulk 有线传输仍受主机调度、驱动和设备完成时机影响，可靠传输不等于
固定完成时间。更完整的约束、理论预算与 Moonlight/Sunshine 借鉴范围见
[协议与性能边界](PROTOCOL_LIMITS.md)。本版源画面、编码与实际 USB 发送检查见
[0.2.5 验证记录](VALIDATION-0.2.5.md)，运动画质对照见
[质量检查记录](evidence/v0.2.5-motion-quality.md)，策略及来源见
[当前实现说明](IMPLEMENTATION.md)和 [VR 时序研究](VR_TIMING.md)；
这些检查限于记录的电脑与测试场景，不代表新的光学延迟验收。

## 诊断与开发

安装包尚无商业代码签名，发行 SHA-256 用于核对文件。DJI 驱动保留原厂签名。
设置、缓存和日志位于 `%LOCALAPPDATA%\DJI Goggles Streamer`；诊断导出不包含
桌面截图或完整 USB 原始数据，不自动上传。卸载保留用户数据和共用驱动。

原 SDK 的 70 个文件中，68 个仍匹配原始基线；唯一运行时代码修改是
`goggles_bridge/engine.py` 的可选 GPU 调度策略。另一处修改纠正
`tests/test_engine.py` 对“查询桌面窗口即创建 D3D 上下文”的错误假设：
尽力设置的 API 合法返回失败时不应导致该测试失败，成功与失败策略另有测试覆盖。
原始基线哈希保留，`sdk-patches.json` 记录两处修改前后哈希与原因。
`python packaging/windows/verify_sdk.py` 校验全部基线和精确补丁，
拒绝未记录或已变化的修改。应用在 `desktop_app/`，新增测试在 `desktop_tests/`。
SDK 的 `gpu_priority_class` 默认仍为 5，`None` 表示不修改 OS 策略；客户端显式
选择 4，原命令行默认行为保留。

0.2.5 保留 0.2.4 的精简 LGPL FFmpeg n9.0.2 二进制和原生补丁，画质设置调整
位于客户端适配层。不能用旧版通用 FFmpeg
替换，否则会缺少原生修复和选项。

开发时先按 [FFmpeg 构建说明](../../packaging/windows/ffmpeg/README.md) 使用固定
源码和工具链构建、验证原生程序，将发行二进制放入 `vendor/ffmpeg` 并与 manifest
的发行 SHA-256 对照。然后用 Python 3.11 x64 安装 `requirements-build.txt`，执行
`python packaging/windows/prepare.py`，再运行 `python -m desktop_app`。
`prepare.py` 会拒绝缺失或哈希不匹配的发行 FFmpeg，不自动退回旧构建。
使用 `packaging/windows/build.ps1` 打包，`-Iscc` 可指定 Inno Setup 编译器。

安装包内的 `_internal/vendor/ffmpeg/source` 包含完整 FFmpeg 上游源码压缩包、
本地补丁、构建脚本、依赖清单和许可；随发行提供的 Source.zip 也包含这些材料。
第三方许可及路径见 [第三方组件说明](THIRD_PARTY.md)。

功能更新递增次版本，修复/测试递增补丁版本。提交格式为
`type(scope): lowercase imperative description`，文档使用 `chore(docs)`。
在用户 fork 的分支开发，保留原 CLI，便于后续回馈上游。
