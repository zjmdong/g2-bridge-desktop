# 0.2.4：固定 1080p100 / 20 Mbps 的时序修正

日期：2026-11-11。Windows / NVIDIA NVENC，固件兼容目标仍为 Goggles 2 的
DJI Virtual Flight USB 路径。此记录区分桌面更新、主机编码输出、USB API 完成与镜片显示。
本轮使用自动化检查，没有要求用户逐轮观察眼镜；没有新的光学端到端测量。

## 已确认并修正的触发条件

**原 SDK 的实时 GPU 优先级请求可以在本机重复触发长输出间隔。**
研究工具在第一张编码帧后查询实际 GPU 调度类别，确认默认类别为 Normal（2），
原请求确实将其改为 Realtime（5），并非将 CPU 优先级误认为 GPU 优先级。
交替对照中，Normal（2）、Above Normal（3）、High（4）均没有出现相同的长尾；
恢复 Realtime（5）后长尾再次出现。更轻的运动纹理源也复现了此结果。

桌面客户端现在请求 **High（4）**。SDK 新增可选 `gpu_priority_class`，命令行默认值仍为 5；
`None` 保持 Windows 原策略。只对本次启动的编码进程、在已有图形上下文后请求一次，
拒绝或不支持时继续串流，并分别记录请求值与应用结果。
没有更改系统电源计划、全局 NVIDIA 设置或 CPU Realtime 优先级。

这是有对照证据的触发条件修正。GPU 完成事件的等待包含输入纹理依赖、驱动调度、编码及线程唤醒；
没有 GPUView 内部轨迹，不能把全部等待归因为某一个 NVIDIA 内核或声称所有驱动都相同。

**独立的采集时钟还会错过源更新边界。**
只保持采集调用间隔 10 ms，不能保证每次拿到一张新图。客户端现在使用同一个 QPC 时钟，
根据真实 `LastPresentTime` 温和调整未来采集期限，并保留 **3 ms 源更新时间余量**。
这不是编码后缓冲，也没有在 USB 发送前增加固定等待。

- 用 16 个真实更新的累计周期和相位中位数判断是否与目标频率相符。
- 每次未来期限最多调整 100 μs；不复制单个桌面时间戳的全部抖动。
- 超时、重复、鼠标单独更新不推动相位；不同源刷新率、宽幅 VRR 和静态画面保留自由时钟。
- 对两周期的观测，只有 DXGI 明确报告 `AccumulatedFrames == 2` 才作为漏采证据，
  避免把真正的 50 Hz 源当成 100 Hz，也避免坏启动相位让估计器永远无法开始校正。
- 发生明显晚醒时，只采当前画面，再安排一个完整周期；不密集重放已经过期的时隙。

主屏与虚拟屏使用同一套捕获、相位判断、转换和编码实现。
源软件自身的渲染速度、显示刷新率、合成与缩放成本仍需分别考虑。

## 测量方法

机器：NVIDIA GeForce RTX 4060 Laptop GPU。物理主屏为 3440×1440 / 100 Hz；
受控测试源为 1920×1080 / 100 Hz 的独立扩展屏。
源程序使用 D3D11 flip-discard、两张交换链缓冲、最大帧延迟 1 和 `Present1(1)`。
最终纹理源仅在初始化上传静态多尺度纹理，逐帧移动取样，内容每 200 帧循环；
不使用 WinForms 定时器或逐帧 CPU 图像上传。

研究探针把 DDA 原始呈现时间、采集序号与 QPC 沿 FFmpeg 自有 FrameData 传到 NVENC 和 muxer，
在固定内存中记录，退出时才输出。Python 侧逐张核对原始 AVI chunk 长度、序号、时钟和因果顺序；
SDK 正常去除 AUD 后的载荷长度单独计数。统计不把 compact PTS 当作实际到达时间。
正式发行二进制没有这套逐帧研究探针，也没有未采用的实验开关。

另对测试图顶部的 frame ID / QPC 标记离线解码，逐个与源程序记录精确匹配。
采集时只在内存保留有限测试数据，解码在计时结束后进行，输出数值后丢弃像素；
没有生成桌面录像或截图作为发行资料。
正式统计排除预热与发送退出指令后的 drain；退出阶段的全部帧仍参与完整性检查。

## 对照结果

以下均为研究二进制的**主机侧**测量。两行 60 秒对照都排除前三秒，采用相同
1080p / 100 fps / 20 Mbps / P4、同一持续运动纹理源；尚不包含眼镜解码或扫描时间。

| 指标 | 原 Realtime GPU 策略，无相位对齐 | High GPU + 3 ms 源相位余量 |
| --- | ---: | ---: |
| 统计窗口输出帧数 | 5,670 | 5,700 |
| 被替换的未编码原始帧 | 30 | 0 |
| 重复的桌面更新时间 | 48 | 0 |
| 编码输出间隔 p99 | 16.647 ms | 11.814 ms |
| 编码输出最大间隔 | 47.160 ms | 12.720 ms |
| 新配置同窗实际源帧率 | — | 100.00 fps |

这说明原先随机出现的几十毫秒长间隔已在该对照中消除，**不等于每帧都严格为 10.000 ms**。
新配置的桌面更新到主机编码输出时间 p50 约 9.06 ms、p99 约 11.57 ms。
两个另外的 30 秒、3 ms 余量样本各有 2,700 张新图，也未出现重复或原始帧替换。

最终图像身份检查完整解码 608 帧，全部 ID/QPC 与源程序精确匹配；正式四秒窗口有
400 张不同画面，零重复、零跳号。源图生成到主机编码输出 p50 为 19.67 ms、p99 为 21.74 ms，
其中源程序自身生成到 DDA 桌面更新 p50 约 11.56 ms，包含同步呈现与合成等待。
这与“已显示桌面到眼镜”的拍屏时间差并非同一指标，不能直接与原作者的约 12 ms 中位数相减。

## 码率与质量

编码目标始终为 **20,000,000 bit/s**，保留 NVIDIA NVENC、P4、ULL、无 B 帧、
无 lookahead、单参考帧、quarter-resolution multipass 和原 VBV/单帧保护。
没有自适应降低分辨率或码率，没有恢复周期性强制 IDR，没有软件编码回退。
BT.709 NV12 转换、色彩兼容设置及图像参考顺序没有改变。

正式发行版的持续运动纹理 USB 样本中，57 个完整一秒窗口均发送 100 帧。
扣除 DUML 分包开销后的编码流估计均值为 19.529 Mbps，范围 19.421–19.628 Mbps，
相对于该样本均值的最大偏差为 0.55%；含协议开销的数据约 20.441 Mbps。
这是该场景的一秒窗口统计，不是每帧等长或任意时间窗口的保证。
CBR 目标不表示每帧必须编码相同字节数；静态或容易编码的内容可能使用更少数据。
没有用 filler NAL 或重复帧把统计值补成 20 Mbps。尚不能声称任意内容的有效码率全程波动小于 1%。

## 排除的候选与发现

- 延迟 `ReleaseFrame` 到下一次 `AcquireNextFrame(0)` 前，在本机造成近乎交替的超时，
  约一半输出重复；下一次成功获取时 `AccumulatedFrames=2`。没有纳入发行版。
- VP 的 speed/rate 提示、MMCSS 和同步 NVENC 对照未提供足够稳定的独立收益，没有纳入。
- 早期复杂 shader 源自身有掉帧，已用其源日志区分，后续换用便宜的周期纹理源。
- 0.5/1 ms 的早期相位余量造成大量重复，已排除。估计器 v1 的资格门槛还会卡在坏相位，
  以 DXGI 累计更新证据修正并加入回归测试后，才进行最终对照。
- 2 ms 的 90 秒样本输出约 99.998 fps、没有编码前丢帧或超过 15 ms 的输出间隔；
  但有 43 次重复。源日志显示其中绝大多数与源自身未按时更新对应，不能全部算作采集失稳。
  3 ms 是当前选用的保守采集余量，并非对所有源的唯一最优值。
- 原有 GPU 单元测试错误地把 `GetDesktopWindow()` 当作创建 D3D 上下文，并要求 best-effort
  API 必须成功。现测试允许合法拒绝，仍验证返回类型和清理；新增 mock 覆盖接受、拒绝、
  不可用 API、句柄、参数及一次性应用行为，实际编码进程的类别另由原生 API 查询确认。
