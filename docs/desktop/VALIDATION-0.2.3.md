# 0.2.3：帧调度、GPU 路径与稳定性审计

日期：2026-11-11。这是 Windows/NVIDIA 发送端修复与验证记录，不是眼镜光学验收。
本轮没有要求用户逐轮观察；验证时未检测到眼镜 USB。不能据此宣称镜片端达到 12 ms、
延迟或码率全程波动不超过 1%，也不能证明眼镜没有丢显示帧。

**结果：已消除可复现的捕获时钟欠速，限制编码前陈旧帧积压，恢复 GPU 内转换，并验证颜色与参考帧完整性。
但本机仍存在编码输出长尾；严格 1% 和零丢帧目标未达到。**

## 源码审阅与约束

[PROTOCOL_LIMITS.md](PROTOCOL_LIMITS.md)。原 SDK 70 个受保护文件保持与
`a34690a58d48f0cd9b43cdeddf39b5efaf024b9c` 相同。用户已允许必要时修改 SDK；
本轮定位到的问题主要在捕获/编码实现，因此补丁位于桌面适配层与 FFmpeg 原生源码，
没有为了扩大码率而放宽原 SDK 的 56,000 字节单帧保护。

对 Sunshine 和 Moonlight 的研究采用固定提交：

- [Sunshine capture](https://github.com/LizardByte/Sunshine/blob/ec2676b60bb8220a1807fc761bc2157e5e6dba63/src/platform/windows/display_base.cpp)：
  参考其绝对时间调度、落后后重新对齐以及只保留最新原始画面的思路。
- [Moonlight receiver pacer](https://github.com/moonlight-stream/moonlight-qt/blob/4113dd26be0907f2edf1805c7b9fd23766e17161/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp)：

- [NVIDIA DirectX/NVENC threading model](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-video-encoder-api-prog-guide/index.html#threading-model)：
  使用每个编码 surface 的完成事件，在事件到达后锁定 bitstream；不是额外积攒多张输出帧。

## 实际更改

1. 原生 DDA 使用 QPC 绝对截止时间、高精度等待定时器和最多 500 μs 的自旋尾段。
   100 fps 只使用一个 10 ms 捕获时钟，移除 240→100 选择造成的 8.33/12.5 ms 交替。
   延误后跳过已过期时隙，不追赶重放旧时隙。自旋最坏约占一个逻辑核的 5%，不是全 CPU 的 5%。
2. NVIDIA 输出在 GPU 内进行全范围 RGB → 有限范围 BT.709 NV12 转换与等比例适配。
   常见 1080p 等尺寸、带鱼屏缩小不再逐帧下载至 CPU 缩放后重新上传。
   仅放大画面拆成 RGB 放大及等尺寸 NV12 转换两步，避免本机 NVIDIA 视频处理器的边缘染色。
   其他厂商 GPU 的源仍需显式内存传递，编码器依然只能是 NVIDIA NVENC。
3. 原始帧队列最多保留一张等待编码的最新画面。编码忙时替换等待中的旧原始帧，
   不影响正在编码的 surface，不丢已编码参考帧；恢复后不消化一串旧桌面。
   这是一项低延迟过载策略，意味着在真实过载时可以丢原始帧，不能称为零丢帧。
4. 使用 NVIDIA 完成事件，保持无 B 帧、无 lookahead、ULL、单参考帧、启动前三个 IDR，
   以及已验证的 quarter-resolution multipass 和两帧模型 VBV。
5. 只为本客户端启动的 FFmpeg 进程请求 Above Normal 与 High QoS。
   不使用 Realtime，不改系统电源计划，不更改全局 GPU 配置。
6. 移除串流 worker 内重复的 250 ms PnP 轮询；独立 USB watcher 仍负责拔插事件。
   无 GUI 时，传输错误后的单次存在性检查也能结束会话并进入虚拟显示器清理。
   实测统计回传不是主要卡顿来源，因此保留已有低开销统计，不把它伪装成端到端延迟。

## 没有采用的改动及证据

- 单纯把捕获频率提高到 400、减少线程、减少 NVENC surface，未解决欠速/尾延迟。
- NVENC 同步/事件模式的 A/B 没有证明尾延迟消失。采用事件模式是为了正确遵循 DirectX 交互模型，
  不是将它宣传为已独立解决随机卡顿。
- 单帧 VBV 和取消 multipass 均未改善本机 DDA 的尾延迟。16 组生成视频对照包含运动及复杂场景切换：
  关闭 multipass、保留两帧 VBV 时，切场关键帧达到 121,213/149,331 B，超过 G2 保护值。
  单帧 VBV 对照的运动码率约 14.09 Mbps、PSNR 37.21 dB；保留 qres/两帧 VBV 约 19.83 Mbps、39.03 dB。
  放宽帧大小或用低质量“恒定速率”换漂亮读数会增加黑屏风险或损失画质，因此没有采用。
- 对照采样确认 GPU 在启动后处于 P0、graphics 2250 MHz / video 1995 MHz，编码尾延迟仍出现。
  没有通过改用户全局电源设置掩盖这个结果。
- 150 秒、15,000 张假 USB 帧的统计/日志/存在性轮询 A/B：封包与假写入 p99 约 0.45–0.49 ms，
  没有超过 15 ms 的间隔。它不能替代真实 USB 测量，但没有支持“统计回传是主要卡顿来源”的假说。

## 剩余长间隔的阶段归因

另用临时 QPC 探针对每张帧记录上传/map、提交、完成事件等待、锁定、复制、解锁与 unmap。
记录写入固定容量内存，关闭编码器时才汇总，不逐帧打印日志；该探针随后从发行源码移除。
各阶段数字、慢帧明细、命令及独立研究补丁保存在 [evidence](evidence/README.md)。
离线生成视频 3,000 帧与实时 DDA 30 秒的结果如下（去掉前100帧的阶段统计）：

| 路径 | 完成事件等待 p50 | p99 | 最大 |
| --- | ---: | ---: | ---: |
| 离线生成视频 | 2.202 ms | 2.714 ms | 28.811 ms |
| 实时 DDA | 7.425 ms | 17.872 ms | 36.487 ms |

DDA 的上传/map、提交、锁定和复制 p99 分别只有 0.050、0.226、0.264、0.009 ms。
最慢8帧都是普通 P 帧、25,000字节，98–99% 时间位于完成事件等待。
因此这些具体尾峰不是启动 IDR、内存大包复制或 USB 调用造成的。
事件等待包含上游 GPU 依赖、驱动调度、硬件编码与线程唤醒，不能把它全称为 NVENC 内核耗时。
源码审查确认事件等待期间没有持有本代码的 D3D11 共享设备锁；scaler 在交付帧前已释放该锁。

再用相同 DDA 源作三路各10秒对照：

| 输入路径 | 完成事件等待 p99 | 主机输出间隔 p99 | 替换的未编码帧 |
| --- | ---: | ---: | ---: |
| GPU NV12（发行路径） | 11.359 ms | 14.094 ms | 2 |
| GPU NV12 下载至CPU后交给NVENC | 6.678 ms | 14.751 ms | 2 |
| 直接 BGRA 交给NVENC | 24.224 ms | 26.749 ms | 13 |

下载屏障能把一部分等待移到编码器之前，但没有改善输出 p99，而且阶段统计不包含上游下载等待；
不能据此认定总延迟更低。直接 BGRA 更差且有历史偏色风险。发行版保留 GPU NV12 路径。
这些样本说明共享纹理/转换依赖可能贡献部分等待，但不是唯一尾延迟来源。

## 像素、边界与生命周期验证

生成画面检查不捕获桌面、不访问 USB。它覆盖 720p/1080p、16:9/带鱼屏/竖屏、放大/缩小/等比例黑边、
16 个颜色、灰阶、逐帧独立身份标记，以及与旧 CPU 路径的 SPS/PPS 比较。

- GPU 原始与解码颜色最大分量误差为 1；灰阶原始 UV 误差 0，解码 UV 误差不超过 1。
- 黑边精确为有限范围黑 `Y=16, U=128, V=128`；所有帧身份顺序完整。
- GPU 和 CPU 各 288 张编码/解码帧，SPS/PPS 一致；GPU 最大帧 36,368 B，低于 56,000 B。
- 保留发现的旧 CPU 基准边缘误差 9 作为非门禁基准，没有放宽 GPU 的像素阈值。
- 原生时钟覆盖 240 万次有理数截止时间与延误恢复检查。
- 最新帧 mailbox 以实际 C 队列实现检查并发、结束、满队列替换、所有权、紧凑 PTS 和默认 FIFO 行为；
  10,014 个帧资源恰好释放一次，10,000 次生产者/消费者压力检查通过。
- 桌面 Python 单元测试 75 项通过。原 SDK 89 项中 87 通过、1 跳过、1 失败：
  `test_gpu_priority_is_best_effort` 的非图形 Python 子进程在本机不接受 D3DKMT 提权；
  被测 SDK 代码与旧版相同，真实 FFmpeg 测试中 GPU priority 请求成功。没有修改 SDK 测试来隐藏失败。

## 理论最好表现与当前实现估计

| 指标 | 协议/硬件边界 | 0.2.3 的可证实行为 |
| --- | --- | --- |
| 分辨率与显示上限 | 单眼 1920×1080，面板最高 100 Hz；Virtual Flight 实际扫描节奏未知 | 720p/1080p，60/75/90/100 fps 目标；不同画面数量仍受源刷新率约束 |
| 码率 | 协议不把 40 Mbps 写死；接收整帧限制比总线带宽先成为工程限制 | 保留 SDK 最大 40 Mbps@100 fps、56,000 B 单帧保护；目标20 Mbps平均约25 KB/帧 |
| 20 Mbps 的 USB 预算 | 100 fps 时约 20.936 Mbps DUML 数据；480 Mbps 原始串行化乐观下界约 0.436 ms/平均帧 | 不加输出节拍等待，不把约0.44 ms宣传为完整USB或总延迟 |
| 捕获排队 | 不提供主机/眼镜显示时钟锁定 | 目标10 ms绝对时隙；最多1张等待编码的原始画面，迟到时以新画面替换 |
| 端到端最低延迟 | 接收/解码/扫描未知，无法从已恢复协议推出精确最小值 | 不人为增加后编码平滑缓冲；已有本机编码长尾，因此无法给出固定12 ms或全程1%的承诺 |
| 最坏延迟 | Windows调度与USB bulk均没有此用途的硬实时保证 | 没有可证明的有限最坏光学延迟上界；错误恢复不等于每帧按时显示 |

最低延迟、永不丢帧、永不重复、永远固定间隔在源或编码迟到时不能同时成立。
本版选择保持画面尽量新鲜，而不是加几十毫秒的缓冲去掩盖长尾。
CBR 是平均预算；静止区域可用更少数据完整表示。不会添加无画质收益的 filler 使仪表维持 ±1%。
1080p100 未压缩 NV12 需约 2.49 Gbps、RGB24 需约 4.98 Gbps，
有损 H.264/USB 2.0 路径不能达到任意画面与 RGB 有线显示器逐像素等价。

## 可重现工具

- `packaging/windows/ffmpeg/build.sh`：完整对应源码、固定版本工具链、原生时钟与 mailbox 检查。
- `packaging/windows/check_gpu_pipeline.py --output <new.json>`：生成视频、像素、帧身份与码流兼容性。
- `packaging/windows/check_capture.py`：实际桌面有限帧数的编码/解码与启动 IDR 检查；不保存画面。
- `packaging/windows/check_encoder_modes.py --output <new.json>`：生成画面覆盖八种分辨率/帧率组合、
  两档NVENC预设和各帧率最高允许码率；不访问桌面或USB，也不将离线吞吐当作延迟。
- `packaging/windows/check_stability.py --seconds 20 --packetize --output <new.json>`：实际桌面输出间隔与封包成本，
  同时记录完整一秒窗口的编码/序列化数据量。其完成状态不代表延迟或码率1%目标达成。
  `--fifo`、`--legacy-clock`、`--synchronous` 可进行受控对照。所有视频字节在内存消费后丢弃，不写图像文件。
- 0.2.2 的 `check_latency.py` 已明确停用；旧 selector 测试可从提交 `f3d8912` 读取，
  不能使用它给新版 native clock/mailbox 生成虚假的生产路径通过结论。

源码、补丁、构建方法与许可随安装包和 Source.zip 分发。没有重新分发 DJI 厂商驱动或私有固件。
