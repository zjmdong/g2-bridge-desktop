# 0.2.6：采集就绪与送帧节奏修复

本版针对采集错过新画面和编码完成时间波动。最终选择保留 3 ms 源相位保护、共享 2 ms 新画面预算与采集时隙加 8 ms 的输出期限，并将预算内的每次实时采集改为 `AcquireNextFrame(0)`，通过最多 250 微秒的定时器间隔重试。早期使用正数 DXGI 超时的候选在实际 USB 串流中仍出现约 20 ms 长尾，已被替换；不能用其较好的 host-only 结果宣称整条链路通过。

NVIDIA NVENC 是唯一编码器。保持 1080p100／20 Mbps／P4、High/CABAC、对称色度 QP -4、qres、无 B 帧与前瞻、单参考帧、VBV 和 56,000 字节单帧保护，保留 0／1／2 秒启动 IDR。没有降低目标码率或更换 RGB 转换策略。

## 最终实现与边界

1. 每次实时新画面重试都传入零 DXGI 超时。未就绪时使用已有高精度定时器等待不超过 250 微秒，再检查；全部重试共享同一 2 ms 绝对期限，并受下一采集时隙限制。期限处最后一次非阻塞检查可接受已经就绪的图像。鼠标更新不能延长预算，也不能冒充新桌面图像。初始格式探测和关闭此选项的原生调用者保留既有策略。
2. 清理路径区分纹理引用与 DXGI 帧所有权。静止画面或超时回退复用最后有效画面，不增加无限轮询或额外帧队列。Windows 唤醒和驱动执行仍可能超时；零参数不等于 API 执行时间为零，也不是硬实时保证。
3. 每帧携带采集时隙的 QPC 时间，经过 GPU 转换、NVENC 与 bitstream filter 后，以该时隙加 8 ms 为输出期限。仅等待剩余预算，迟到立即发送，不顺延后续期限，不丢弃编码参考帧。现有单包输出队列和 mux 当前持有的包仍存在，不能称为无缓冲。
4. SDK 收到完整帧后仍立即写入 USB，无新的 Python 发送节拍器。正常产品路径没有逐帧测量日志或额外设备回读。开始日志的 `capture_fps` 改为实际选择值，避免继承 SDK 默认 240 的误导字段。

两个新原生选项默认关闭，客户端显式选择 `fresh_wait_us=2000`、`delivery_delay_us=8000`。SDK 协议及既有两处审计补丁未变。64 KiB stdout pipe 与 5 ms 源保护实验均未采用。

## 测量如何区分真实画面与平均帧率

测试主机使用 RTX 4060 Laptop GPU。生成纹理源每张画面携带帧 ID 和渲染 QPC，源呈现也记录独立 QPC。串流期间只保留有界 RAM 中的 AU、到达与写入时间；停止后才进行 CPU H.264 解码核对身份。CPU 解码用于核验，不是软件编码。没有保存实际桌面录像，也没有要求用户目视参与本轮检查。

夹具使用三个 swapchain buffer、MaximumFrameLatency 2；这是生成源自己的呈现配置，没有给产品增加三个视频缓冲。源渲染到主机年龄包含夹具呈现队列，不能当作采集或光学延迟。100 Hz 配置、100 AU/s 和 100 个不同源图像分别检查。

USB 定位工具在 `AviPacketStream.feed` 返回完整 AU 后记录到达时间，并记录完整视频 `VerifiedTransport.write` 的开始和结束。只在单一 parser、无重启／超大帧丢弃、逐序长度一致和时间因果成立时匹配，不根据相同长度猜测跳帧后的对应关系。到达至写入开始包含队列、控制循环和 packetization，不能进一步单独归为队列时间。

主屏夹具的早期运行曾被聊天窗口遮挡，包含标记检查失败的运行和无遮挡状态无法确认的运行，全部排除验收。主屏夹具随后只在测试生命周期内置顶，保留不激活、Escape 与 30 秒上限。启动时用 `CREATE_NO_WINDOW` 隐藏控制台，并显式指定 `STARTF_USESHOWWINDOW`／`SW_SHOWNORMAL`，避免继承父进程的隐藏状态；仅前者不足以保证可见。检查置顶样式与标记位置命中窗口归属，并先验证短时源身份。它不会修改显示模式；前台请求可能被系统拒绝，不能由请求成功推断无遮挡。

## 选型实测：非阻塞重试，真实 USB，60 秒

以下是选择最终策略的实验数据，来自 `usb-probe-nonblocking-60.json` 及其 host 报告。该实验使用带诊断探针的二进制，SHA-256 为 `96e311e0c25e041cd42ce197429a86187e746febaac6da2c19bd7581ea3f31fb`；它不是随后生产构建的发行身份。

条件为独立扩展屏 1920×1080／100 Hz、生成动态纹理、NVENC P4、20 Mbps；排除前三秒启动阶段。共收到并成功发送 6004 个完整 AU，清理无错误。host 写入窗口保留 5702 帧；身份窗口按首个 AU 起算至 60 秒，保留 5700 帧，两种窗口边界不能混为同一个分母。

| 主机阶段 | P99 | 最大值 | 超过 15 ms 的间隔 |
| --- | ---: | ---: | ---: |
| 完整 AU 到达间隔 | 10.4233 ms | 10.9938 ms | 0 |
| USB 写入完成间隔（host 汇总） | 10.5770 ms | 11.2204 ms | 0 |
| AU 到达至写入开始，队列与 packetization 合计 | 0.5314 ms | 0.9653 ms | 不适用 |
| 完整视频 USB 写入耗时 | 1.0007 ms | 1.5781 ms | 不适用 |

逐序关联表从其第一条稳态写入开始计算相邻间隔，少一个跨边界间隔，因此 USB 完成 P99 为 10.5776 ms；这是与 host 汇总定义不同造成的微小差异。对应原生探针窗口未记录到晚于输出期限的到达。以上只证明此有限场景的主机链路改善，不能证明镜片每次呈现均为 10 ms。

## 同一运行的源身份仍有重复与遗漏

6004 个解码 `(ID, render QPC)` 全部与源日志匹配。稳态身份窗口为 5700 个输出、5589 个不同源 ID、111 次重复，跳过 62 个已提交的源 ID。源渲染到主机年龄中位 32.689 ms、P99 42.8492 ms，含源队列，不能解释为 NVENC 或 USB 耗时。

接收到的首尾 ID 之间，源实际提交 5651 张，约 99.14 张／秒。109 次源间隔超过 15 ms，折算为 111 个超出标称间隔的时隙，并出现 62 次小于 1 ms 的追赶提交。这与 111 次重复、62 个跳号数量对应，但数量相符只支持关联，不证明全部遗漏均在源端。

62 个遗漏 ID 的 DXGI 呈现统计分类如下：

- 0 个明确被采样统计记录为已呈现。
- 16 个位于相邻两个 VBlank 的已观察 Present ID 之间，无法各自占一个独立 VBlank。
- 11 个所在区间的提交编号增量超过刷新增量，只能确认区间内存在呈现选择，不能逐个确定。
- 35 个采样区间仍允许中间图像曾呈现而未被观察，归因未解决。

因此不能声称零丢帧，也不能将 62 个全部归为 DDA 采集丢帧或全部归为 DWM 丢帧。此前正数超时版本一次真实 USB 运行是 38 次重复、零跳号，但其源没有追赶 burst，且输出有超过 15 ms 的长尾；来源节奏不同，不能把两次计数直接当成严格同源 A/B。

## 已排除或被替代的方案

| 方案 | 实测与决定 |
| --- | --- |
| 正数 DXGI 超时的新画面重试 | 已构建的早期候选在 `usb-release-retry.json` 中 USB 完成间隔 P99 18.4467 ms、最大 21.0767 ms。另一次逐阶段定位仍有约 24 ms 长尾，主要已出现在 AU 到达阶段。不是最终成功结果，改用全部零超时的实时重试。 |
| stdout pipe 增至 64 KiB | 对照仍有约 20.8 ms 最大 USB 完成间隔与 12 次超过 15 ms；原 pipe 对照也有长尾。没有消除上游等待，不采用。 |
| 源相位保护从 3 增至 5 ms | 非阻塞路径的该运行出现 299 次重复、219 个跳号，源年龄中位约 34.63 ms；USB 最大间隔约 21.85 ms，其中一次 USB 写入本身约 12.64 ms。来源不同限制因果推断，但没有足够收益支持增加等待，保留 3 ms。 |
| 主屏 fresh budget 4 ms／source guard 5 ms 对照 | 分别记录在 `release-primary-fresh4-valid-20.json`、`release-primary-guard5-20.json`。两者都残留 1 次重复、1 个已呈现源 ID 遗漏；后者额外增加约 2 ms 源年龄。未证明消除问题，均不采用。 |
| 延后释放 DXGI 帧、降低 GPU 优先级 | 前者出现大量重复／跳号，后者没有一致改善，均未采用。保留既有 High 4 GPU 请求。 |

此前只读 stdout 的 20／60 秒候选，以及无遮挡主屏 20 秒对照，曾显示输出 P99 约 10.5 ms；它们支持研究输出调度，但没有真实 USB 压力，且使用被替代的正数超时二进制，不能替代最终生产程序的复核。早期 60 秒候选仍有 19 个超过 15 ms 的间隔。

一次历史探针长尾中，独立 renderer 等待约 54 ms、DDA 调用约 39 ms、编码阶段约 49 ms，几乎同时解除。代码审查未发现 NVENC 在持有 FFmpeg 私有 D3D11 mutex 时等待完成事件；共同 GPU／DWM／驱动或 OS 调度仍是可能因素，尚未进一步定因。期限调度不能补出这种暂停期间不存在的源图像。

## 构建与回归

从固定 FFmpeg 上游归档及更新后的原生补丁构建。实际提取的非阻塞采集函数通过 16 项 CPU mock，覆盖零超时、250 微秒定时器重试、静止源、鼠标更新、共享期限、最终检查、迟醒及资源所有权；CPU 模型不是驱动时序证明。10,000 帧输出期限模型、源时钟和 mailbox 检查保留。客户端 89 项测试、公开研究工具 19 项测试（基础 8 项与 USB 定位工具 11 项）通过，SDK 70 文件基线及两处精确补丁校验通过。

同一生产 FFmpeg 的 `release-final-modes.json` 检查通过全部 32 种组合：主屏／扩展屏 × 720p／1080p × 60／75／90／100 fps × P1／P4，每种输出 20 帧，进程正常退出并检查帧大小。这是短时模式兼容检查，没有打开 USB，也不能替代长时间流畅度验收。

`release-final-gpu-colour.json` 的 6 种生成几何／像素场景通过，每种 48 帧；CPU 参考转换与 GPU 转换的 raw、encoded、decoded 各阶段分别累计 288 帧。两条编码路径均使用 NVIDIA NVENC，CPU 参考是像素转换而非软件编码。原始 GPU 样本容差保持 2 个码值，解码样本容差保持 4 个码值；保留帧顺序、码流兼容和单帧预算检查。旧 CPU 转换路径的颜色误差只作诊断对照，不据此放宽 GPU 颜色门槛。这是生成图检查，不是眼镜光学显示或实时节奏检查。

桌面构建通过，冻结程序的 NVIDIA 编码环境与 USB watcher 清理检查通过。安装包 `DJI-Goggles-Streamer-0.2.6-Setup.exe` 为 53,102,086 字节，SHA-256 为 `6b55cd28603333966f53a3a7b6d4a8f6b2cebc95eef218e6136db7a0e694c3a7`。

安装升级已完成，退出码为 0，无管理员提权。`installed-final.json` 校验 215 个已安装文件与打包文件逐项匹配，缺失／不匹配均为 0，安装版本为 0.2.6，FFmpeg／ffprobe 哈希与本页生产身份一致。设置文件逐字节保留；本机原设置为 60 fps／20 Mbps／P4／扩展屏，没有被重置到产品默认值。已验证 GUI 可启动，标题为 `DJI Goggles Streamer 0.2.6`。自有测试扩展屏已退出活动状态，主屏 3440×1440／100 Hz 保留。

最终生产 USB 结果已在前置章节列出；主屏、模式／像素检查和打包结果另外绑定其执行二进制，汇总于 [发布检查摘要](evidence/v0.2.6-release-validation.json)。不得将早期候选 `4bd161c5…` 或诊断探针的检查结果重新标记为最终生产二进制执行。完整选型数值和原始报告身份见 [帧身份与节奏证据](evidence/v0.2.6-cadence.json)；复现工具与安全启动方式见 [frame_cadence](../../packaging/windows/frame_cadence/README.md)。

## 未达成的保证

没有新的显示器到镜片光学测量，不能宣称达到原作者约 12 ms，也没有证明全程延迟／码率波动小于 1%、零重复／遗漏、每帧大小相等或与无压缩有线显示器等同。固定 20 Mbps 是编码目标，不是每帧等字节填充；协议仍没有镜片 VSync／呈现反馈。当前结论限于记录条件下可定位的主机链路改善及明确保留的源端、系统和接收端边界。
